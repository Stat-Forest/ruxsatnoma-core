# Ruxsatnoma backend — conventions

FastAPI modular monolith for the forest-permit system. Architecture, DB schema and API contracts live in the docs repo: `../docs/design/01-struktura-monolita.md`, `02-shema-bd.md`, `03-api-kontrakty.md`; decisions — `../docs/decisions.md` (source of truth).

**Before any work read [`.claude/lessons.md`](.claude/lessons.md)** — the accumulated gotchas of this codebase (`Rule` / `Why` / `How to apply`). If a lesson covers the area you are touching, it overrides your instinct; the entries exist because each one already cost a review round or a production-shaped bug.

## Run / test

`make help` lists every target; **`make check` is the local gate and mirrors CI exactly** (single Alembic head + lessons budget + ruff check + format check + pyright + bandit + pytest) — run it before every commit, together with `uv run pre-commit run --all-files`. The raw commands behind it:

```bash
uv sync
docker compose up -d          # PostgreSQL 16 + PostGIS, MinIO; test DB auto-created
uv run alembic upgrade head
uv run uvicorn app.main:create_app --factory --reload
uv run pytest -v              # integration tests need docker up (serial; one DB)
make test                     # what CI runs: -n 4 --fresh-db, ~3 min instead of ~14
uv run ruff check . && uv run ruff format --check .
uv run pyright                # type check (standard mode, decision #39)
uv run python -m app.seed organizations app/seed/data/organizations.example.json   # reference data
```

### Running the suite in parallel

`make test` runs `pytest -n 4 --fresh-db`; the same `-n 4` is in CI. Measured
2026-09-06 on this machine: **832s serial -> 169s on four workers** (1832 tests).
Most of that time is not computation — the suite waits on PostgreSQL and MinIO
round-trips (CPU was busy 37% of the wall clock), which is exactly what
parallelising buys back. Eight workers reach 133s, only 21% better than four,
so four is where the curve flattens.

Two things make it work, both in `tests/conftest.py`:

- **A database per worker.** `_use_a_database_of_this_workers_own()` rewrites
  DATABASE_URL_TEST (and DATABASE_URL) to `<base>_gw0`, `<base>_gw1`, ... and
  `_migrated_test_db` creates and migrates each on demand. Nothing here rolls a
  test back, and `test_migrations.py` drops every table in its database — two
  workers on one database would wipe each other's tables mid-INSERT. This nests
  inside the per-worktree split in `../CLAUDE.md`: a worktree whose test DB is
  `..._311` gets `..._311_gw0`, so parallel sessions still never meet.
- **`--fresh-db`.** Fixtures place random polygons and never clean up. Left to
  accumulate, a new box eventually lands on an old one and the failure surfaces
  as `ERR-GIS-002` in a fixture that has nothing to do with geometry, or as an
  overlap sweep counting a permit from a previous run. Re-creating the database
  costs ~7s per worker, in parallel, and is why the suite is green rather than
  8-failed-42-errors flaky.

Debugging one file is still fastest serial and on the existing database:
`uv run pytest tests/modules/permits/test_issue.py`. `PYTEST_XDIST_WORKER` is
unset there, so no rewriting happens at all.

## Hard rules

- **English everywhere** in code, comments, docstrings, commit messages (decision №35). Existing Russian comments from the stage-2 skeleton stay until touched. No AI attribution in commits.
- **Async only** (№26): asyncpg, SQLAlchemy 2 async, httpx; no sync drivers, no `time.sleep`.
- **Module boundaries** (design/01): `app/modules/<name>/` with `router → service → repo → models` (+ `schemas`). Cross-module calls only via the other module's `service`; upward signals via synchronous in-transaction events; readers (reports, dashboard, search, oversight, archive) plus gis/norms-over-`permits` and norms-over-`applications` (3.9a ruling 20 — `norms/repo.py` only, five columns, no writes) get read-only table access. `app/core/` never imports domain modules.
- **Transactions**: `get_db` commits on success, rolls back on exception (№37). Services may commit earlier explicitly.
- **Errors**: raise only via `err("ERR-…")` from `app/core/errors.py`; the catalog mirrors `../docs/tz/10-klassifikatory.md`. Single response format with `correlation_id` — do not invent ad-hoc error bodies.
- **Time**: store UTC (`timestamptz`), display Asia/Tashkent. Money/norms — `numeric`, never float.
- **Migrations**: Alembic autogenerate is wired with GeoAlchemy2 `alembic_helpers` (protects PostGIS tables) — do not remove; keep `sqlalchemy.url` in `alembic.ini` empty (URL comes from settings/attributes); naming convention lives on `Base.metadata`. A guard test asserts an empty autogenerate diff.
- **Audit invariant**: every state-changing action calls `audit.service.log(db, action=…)` in the same transaction (no commit inside — `get_db` commits both together). Action codes: `"<object>.<verb>"` in English, constants live in the acting module.
- **Auth**: protect routes with `Depends(get_current_user)` / `require_permission("code")` from `app/modules/auth/deps.py`; permission codes are registered in the owning module via `auth.permissions.register`. `sys_admin` is a superuser: `require_permission` lets it through before checking codes (decision #41 ruling 2; the action is still audited, and the DB-level append-only triggers on `audit_log` are unaffected). Zone scoping — `app/core/abac.py` `zone_filter`. Denied/error audit entries follow the early-commit pattern: write counters + `audit.service.log(..., result="denied")`, `await db.commit()`, then `raise err(...)`. **This is a property of THIS CODEBASE, not of one module** — `signatures.service.sign()` does it today, and by the same reasoning `notify()` on an undeliverable recipient and 3.10's Payme paths may tomorrow — so it is also a rule for the CALLER: *a function that commits its refusal commits everything else you have pending — call it before you create state you would not want kept.* Applicant flows (3.2b): the OneID/E-IMZO/OTP-sender adapters live at `app/modules/integrations/adapters/` since 3.4 (mock/real selected by `*_MODE` env; `app_env=prod` forbids mock); an `applicant`-role user without their own `applicants` row is gated to `/auth/*`'s registration-exempt paths plus `/api/v1/refs/*` only — anything else raises `ERR-AUTH-008` (checked in `get_current_user`, same pattern as must-change-password); legal-entity representations are checked effective on read (`status='active'` and not past `valid_until`, via `business_today()`), and since 3.4 a daily job also flips expired rows to `status='expired'`.
- **Outbox & workers (3.4)**: every outbound message is enqueued via `integrations.service.enqueue(db, destination=..., payload=...)` IN the business action's transaction — never send inside a request. Delivery is the outbox worker's job (retry/backoff → `dead` = the DLQ; admin requeue via `/admin/integrations/*`). Workers (outbox loop + APScheduler scheduler behind a PG advisory lock) run embedded in the API lifespan when `workers_mode=embedded` (default) or standalone via `python -m app.workers [outbox|scheduler]`; tests set `WORKERS_MODE=off` (root conftest). Periodic jobs live in `app/workers/jobs.py` and audit their data changes with `user_id=None`, `correlation_id="job:<uuid>"`. Sender registry: `integrations/senders.py` (`register_sender`). New destinations must never echo the payload into raised exceptions — `last_error` is admin-visible and logged.
- **Rate limiting & idempotency (3.4)**: anonymous auth routes (`/auth/login`, `/auth/otp/request`, `/auth/eimzo/challenge`) carry a per-IP token bucket (`app/core/ratelimit.py`, limits in `system_settings`, 429 `ERR-SYS-006`). Critical POSTs of 3.9/3.10 must attach `auth.deps.idempotency_context` and call `ctx.save(db, status_code=..., body=...)` before returning (mechanism in `app/core/idempotency.py`, 409 `ERR-SYS-005`).
- **Notifications (3.5)**: `notifications.service.notify(db, event_code=..., recipient_user_id=..., params=...)` is how any module talks to a user — call it inside the business transaction, never from a background task of its own; `params` values that are not JSON primitives (a `Decimal` amount, a `date`) are coerced to `str` before storage, so a caller never has to think about the JSONB bind. `inapp` is always written (С19: legally significant notifications reach the cabinet even when other channels are off); **`sms` is closed to every role but `applicant` (decision #150) and is ALWAYS rendered in `uz_latn` (`SMS_LANGUAGE`, decision #151 — only the Latin texts are moderated by Eskiz, and an unmoderated text does not arrive with nothing reporting it)** — staff read the same notification in the cabinet they already have open, so `_recipient_reachable` refuses the channel by ROLE, in one place, and a caller never passes `channels=` to arrange it. A test whose recipient must receive an SMS has to create them with `role_code="applicant"`: `make_user`'s default is `executor_staff`, and an SMS assertion on the default silently stops testing anything. `sms`/`email` ride the 3.4 outbox (`sms`/`email` destinations in `integrations/senders.py`) and are never sent synchronously from a request. The `notifications_sms_enabled` ops kill switch means two different things by position: at enqueue time it skips the channel, at DELIVERY time it *raises* (`ChannelDisabled`) so the outbox's backoff ladder PAUSES the queue — only a permanently unreachable recipient may fail a notification and return. Texts live in versioned `notification_templates` rows (admin CRUD under `notifications.templates.manage`, supersede-by-archive, never an in-place rewrite), not in code — the one exception is the OTP text (`integrations/adapters/otp_sender.py::OTP_TEXT`), which has no recipient to pick a language for. A new outbox destination must be registered somewhere a standalone `python -m app.workers` process actually imports (see `app/workers/outbox.py`'s import of `notifications.service`), or delivery dies as `unknown destination` — invisible in every in-process test, total in production.
- **Deploy notes (3.4, extended 3.5)**: run uvicorn with `--proxy-headers`/`--forwarded-allow-ips` behind a proxy — the rate limiter keys on `request.client.host`, and without them every client shares the proxy's IP (one bucket = a system-wide login outage); with `workers_mode=off` a standalone worker process is mandatory or OTP delivery silently stops; deploying a new `secret_key` (or the 3.4 HMAC switch itself) invalidates in-flight OTP codes (≤5-min TTL — harmless, but know it); `PUBLIC_BASE_URL` must be the externally reachable origin or Eskiz's delivery reports go nowhere (a local origin is now rejected outright under `sms_mode=real`); `ESKIZ_CALLBACK_SECRET` must be long and random — it is the only authentication on that endpoint; `sms_mode=real` additionally requires `ESKIZ_EMAIL`/`ESKIZ_PASSWORD`/`ESKIZ_SENDER`, `email_mode=real` requires `SMTP_HOST`/`SMTP_FROM` (plus credentials for an authenticated relay); Cyrillic SMS bill at 70 characters per part, so template edits change cost. **3.11a**: `GET /api/v1/public/permits/check` is the first route the open internet reaches with no credentials — `qr_check_log` deliberately records no IP and no personal data, and `app/core/logging.py` drops that path's uvicorn access-log line so the process log does not undo it from outside (that line would carry the visitor's IP AND the printed QR token in plaintext). A deployment that fronts the app with its own access logging (nginx, an ingress, a sidecar) has to exclude the same path itself — the filter reaches uvicorn's logger, nothing further out. Also 3.11a: **WeasyPrint needs the Pango/GLib/HarfBuzz system libraries in the image** (`libpango-1.0-0 libpangoft2-1.0-0 libharfbuzz-subset0` on Debian) — `uv sync` does not install them, and without them permits cannot be issued at all; the exact lists and the macOS dyld note are in `README.md`. **3.9a**: **until a `doc_types` classifier item with code `benefit_proof` is seeded and ACTIVE, no benefit can be claimed on any submission** — the check is fail-closed by design, so an absent or archived item refuses the claim rather than accepting any attachment. Migration `0024` seeds it, and an operator who archives it through the admin CRUD turns every benefit claim into a refusal. This sits on the go-live checklist beside the `coef_sb:*` drafts (both are "loudly wrong beats silently wrong", and both need a human action before the first real filing).
- **GIS (3.6a)**: geometry lives ONLY in `contour_versions.geom` and `layer_features.geom` — a `contours` row is identity, nothing more. Every geometric predicate (containment, intersection, area, validity) runs INSIDE PostGIS via `func.ST_*`/`text()`, never in Python — `gis.repo` and `gis.checks` build SQL, PostGIS answers it. GDAL (`pyogrio`) is blocking C code: file parsing (`gis.importer.parse`) only ever runs through `asyncio.to_thread`, never on the event loop, even though it already executes inside a worker rather than a request. `contour_versions.area_ha` is always `ST_Area(geom::geography) / 10000`, computed on insert — the area of record; the source file's own figure lands in `declared_area_ha`, reference only, never read by a calculation (fee, `S_available`, anything). The four topology checks (`gis.checks.run_checks`) split blocking from advisory on purpose: `validity`/`within_fund`/`overlap` block publication (`ERR-GIS-003`, `details.checks` carries the full report); an intersection with a `restrictions`/protection/fire-ban feature is always a `warning`, never a `fail` — that decision belongs to the norm (3.7) and the application review (3.9), which read the very same check rows, so moving a layer into the blocking set is a product decision, not a refactor. `ERR-GIS-005` (409) is this module's own state-conflict code (a taken contour number, an edit to a non-draft row, a bad batch transition) — `ERR-SYS-005` means "Idempotency-Key conflict" and must never be reused here: `POST /gis/imports` requires an `Idempotency-Key` (3.4's mechanism, `auth.deps.idempotency_context`, whose first consumer this is), so on that route the two codes really do arrive side by side and a client has to tell a duplicate contour number from a replayed request.
- **Norms (3.7)**: **every number the engine uses is a versioned `rule_parameters` row** — the calculator never falls back to a literal, and a parameter that is not published and effective on the calculation date raises `ERR-NORM-004` naming itself (`details.code`). The one hard-coded value in `norms/calculator.py` is `RULE_CODE_VERSION = "norms-1.0.0"`, and it is not a quantity: it is the identity of the arithmetic, stored on every calculation, bumped when a formula changes SHAPE and never when a value changes — that is what the effective periods are for. **The calculator is pure**: `calculator.py` is synchronous, `Decimal`-only and never receives an `AsyncSession`; `params.py::load_snapshot` is the only thing that queries, and `input_snapshot` is literally the serialized snapshot (parameters, tariff rows, norm, the committed load and its source), so a stored row can be recomputed years later without the database. Money rounds `ROUND_HALF_UP`, never Python's default banker's rounding, and rounding is itself a parameter (`rounding_money`, `rounding_heads`) applied ONCE, at the end — an unrecognised mode raises rather than falling through to a branch. **A preview reports, a save refuses**: `preview` and `save_calculation` share one `service._compute` so they can never drift, and differ only in what a BLOCKING check does — the preview returns it as data in `checks[]` (an applicant must be able to SEE that a herd is too large), the save raises the mapped `ERR-NORM-001/002/003` with the whole report in `details.checks`; a broken INPUT (a missing parameter, an unknown benefit code) is an HTTP error on both paths. `checks.run_checks` is the shared entry point 3.9 also calls, so its own guards are the root fix: a reversed period, or one longer than `MAX_PERIOD_DAYS`, is refused fail-closed before any check runs. A fire ban blocks; a `restrictions`/protection intersection only warns (the call 3.6a deliberately left to this module — decision #49 ruling 16). **`coef_sb:*` ships as DRAFTS** (ВМҚ 689 annex 5 has not arrived) and the engine reads published rows only, so a fresh database *cannot compute a grazing fee at all* until a central admin publishes those ten rows — deliberate and visible, a go-live checklist item, never something to "fix" with a default. `tariffs`/`rule_parameters` are maker-checker in the DB CHECK as well as in the service (a migration-seeded row has `created_by IS NULL` and is exempt); archiving a PUBLISHED row additionally requires `norms.tariffs.publish`, archiving one's own draft does not. `calculations` is append-only at the database level — a recalculation is a new row. `norms` is a level-3 module: it reaches `gis` only through `gis.service` (`published_version`, `contour_organization`, `features_intersecting`) and reference data only through `admin.repo`/`admin.service`. Its two codes: `ERR-NORM-004` (422, a missing/unusable parameter) and `ERR-NORM-005` (409, a state or period conflict — `not_draft`, `bad_transition`, `period_overlap`, `not_maker_checker`, `no_published_contour`).
- **Applications (3.9a)**: **the event bus is synchronous and runs INSIDE the publisher's transaction** (`app/core/events.py`, design/01 rule 4) — a handler that raises rolls the publication back with it, which is why `POST /approve` never answers `APPROVED`: 3.10a's invoice subscriber has already moved the application to `INVOICED` in the same transaction. **Subscriptions and provider registrations live in `app/event_subscriptions.py`, never in `main.py`** — both `create_app()` and the standalone `python -m app.workers` import it, so a subscriber cannot be present in one process and absent from the other; keep every registration idempotent (a membership check before the append), because the autouse test fixture restores `events._SUBSCRIBERS` only. **A level-4 module moves an application only through `applications.service.set_status`** — never a direct `UPDATE applications.status`, never an import of `applications.repo`/`.models`; `APPLICATION_TRANSITIONS` is `tz/05` and `tests/modules/applications/test_public_surface.py` pins both it and the public surface (`get`, `current_calculation`, `set_status`). **The signed package bytes are canonical and their SHAPE MUST NEVER CHANGE** (`service._package_bytes`): sorted keys, `application_id` inside and `submission_id` deliberately outside (a per-attempt value `GET /package` cannot know would make every fetched package differ from the bytes `submit` verifies). **The contour version they name is the CURRENT published one only while the application is a DRAFT; from SUBMITTED onward it is the frozen `applications.contour_version_id`** — `gis` publishes one version per contour and it may be superseded at any time, so pricing the current one would make the head's decision signature attest to version B while the application and the permit printed from it name version A, and a verifier re-deriving the bytes from the stored row would find the signature invalid. Both signatures are taken over those bytes — a submission as `("application_submission", <the SUBMITTED history row's id>, "application_submit")`, a decision as `("application", <application id>, "application_decision")`. **Three vocabularies share the word "application" and none is interchangeable**: the bus name (flat, `application_submitted`), `notification_templates.event_code` (dotted past participle, `application.submitted`) and `audit_log.action` (dotted present-tense verb, `application.submit`) — one `submit()` writes all three for the same moment, and passing the wrong one at the notification seam fails SILENTLY (`notify()` writes a raw fallback in-app and sends nothing at all by SMS or e-mail). `events.NOTIFIED_EVENT_CODES` lists the DOTTED codes and is the one place a new notification is registered; two guard tests hold it against the seeded templates and against the module's own `NOTIFY_*` constants. **The submission's order of operations is the design, not a preference**: price through `norms.service.preview` (stores nothing) → run the checks → `sign()` → only then allocate the number and `save_calculation`. `sign()` commits the caller's session on every refusal path, so a calculation written before it would survive the refusal as a live under-billing row nothing can delete; the `application_checks` rows and the frozen `contour_version_id` are what it IS right to leave behind (they are evidence of a genuine attempt). **`norms.service.save_calculation`'s guard is actor-dependent** — the owner may bind only in `DRAFT`/`RETURNED`, `applications.review`/`decide` additionally in `SUBMITTED`/`IN_REVIEW`/`PENDING_INFO`, `applications.view_any` gates nothing, and APPROVED-and-beyond is closed to everyone including `sys_admin`; beside WHO and WHEN it also checks WHAT, refusing a calculation whose `contour_id` is not the application's own (`calculation_for_another_contour`) — comparing the activity and the period too would need ruling 20 amended for two more columns — and it is reached through **ruling 20's read-only window into the `applications` table: `norms/repo.py::application_facts`, five columns, that file only, no writes and no read from `norms/service.py`** (a sixth column needs the ruling amended, in `design/01` rule 5). **`POST /cancel` accepts DRAFT, SUBMITTED and IN_REVIEW as a SOURCE and nothing else, deliberately narrower than the transition table** (ruling R26): `INVOICED -> CANCELLED` is `tz/05`'s and stays in `APPLICATION_TRANSITIONS` for 3.10b to drive through `set_status`, because a cancel taken from this route would lock application-then-invoice and invert the invoice-then-application order `payments` documents for itself — and `applications` may not take the invoice lock itself (level 3 -> level 4). `ERR-APP-004` (409) is this module's state-conflict code; `ERR-GIS-005` carries two meanings on the submit path and a client must read `details` to tell them apart. **The review workflow (3.9b)** extends this rather than sitting beside it. `sla_deadline_at` is a STORED, SHIFTED timestamp — moved forward by the length of each closed `PENDING_INFO` pause at the moment the pause closes (`sla.shift_deadline`, whole seconds, never a running sum recomputed on read) — and an OPEN pause suspends the clock REGARDLESS of what the stored deadline reads: `is_overdue` checks `status != 'PENDING_INFO'` before it ever compares `now()` to the column. `application_conclusions` and `calculations` are both append-only, for the same reason `application_status_history` is: a specialist's correction, or a recalculation (`POST /recalculate`, itself routed through `norms.service.save_calculation` rather than writing a row directly), is a NEW row, never an edit of the one it corrects, because a later decision may already have been signed over what the earlier row said. The veterinary and cadastre adapters (`integrations/adapters/vet.py`, `cadastre.py`) are MOCK-ONLY until a real contract exists (`VET_MODE`/`CADASTRE_MODE` default `mock`, `real` raises `NotImplementedError`, decision #42 ruling 2) — and unlike every other adapter in this codebase, prod is allowed to STAY mock: `get_adapter()` refuses only to ANSWER from one in `app_env=prod`, so a live vet/cadastre check in production always falls through to the `application_checks` paper fallback under maker-checker (`created_by`/`confirmed_by`/`confirmed_at`, migration `0025`) rather than a mock silently returning a fabricated `"pass"` indistinguishable on the wire from a real registry answer.
- **Payments (3.10a)**: Payme is the client, we are the server — `POST /api/v1/webhooks/payme` (`app/modules/payments/payme_router.py`) answers **HTTP 200 to everything** and lives entirely outside the `ERR-*` envelope; a Payme failure is a `{error: {code, message}}` body inside that 200, never a raised `err(...)`. `payme.py` is the RPC dispatcher — `payme.handle(db, method, params, *, now)`, pure of HTTP, independently unit-testable; `payme_router.py` is only the thin shell that guarantees the 200. Amounts cross that wire as **integer tiyin** (`to_tiyin`/`from_tiyin`, `integrations/adapters/payme.py`, re-exported from `payments/payme.py`) while every table (`invoices.amount`, `allocations.amount`, …) stays `Decimal` — the conversion happens at the wire boundary only, nowhere else. Idempotency on that route is keyed on **Payme's own transaction id** (`provider_transactions` unique `(provider, external_id)`) — never our own `Idempotency-Key` middleware, which belongs on `POST /invoices/{id}/pay-intents` (the route our own client calls) and nowhere on the Payme side. The `allocations` ledger records money that **arrived**, never a claim: entries are written on `PerformTransaction` (state 2) against the `provider_transaction`, never at invoice-issue time, and a 50/50 split's odd tiyin always goes to the `budget` half, never `recipient` (`payments/ledger.py::split`). An invoice becomes `PAID` only on the provider's confirmation — never optimistically, never from `pay-intents`. An application's status moves only through `applications.service.set_status` (never a direct `UPDATE`, never an import of `applications.repo`/`.models`); the two subscribers that call it — `application_approved` (issues the invoice, → `INVOICED`) and `application_cancelled` (cancels any in-force invoice) — register in `app/event_subscriptions.py`, never `main.py`. `ERR-PAY-004` (409) is this module's state-conflict code, for an invoice that cannot be paid in its current status. **Deploy requirement**: the Payme endpoint must be rate-limited at the reverse proxy — the cashbox key (`Authorization: Basic base64("Paycom:<key>")`) is its *only* authentication, and this codebase's own `app/core/ratelimit.py` raises a 429 this route may never return.
- **Permits (3.11a)**: **the document is rendered exactly ONCE, at issuance, and `permits.doc_hash` is frozen over the stored bytes** — every one of the 3+1 ERI signatures is taken over *those* bytes, which is what makes `signatures.service.require_complete` mean what it says. **Nothing re-renders a permit, because 3.11a exposes no entry point that could**: `service.issue` renders once and `GET /permits/{id}/pdf` serves the stored file. `ERR-PERM-002` («документ уже подписан и не может быть перевыпущен») is therefore registered in `app/core/errors.py` and raised by nothing — reserved, not dead: 3.11b's duplicate register (нусха) must copy those same bytes rather than re-render them, and the day any path can reach the renderer with an already-signed permit, that path raises this code. A corrected permit is a revocation plus a new one, or a duplicate of the same bytes — never a re-render. **The signatory must hold the role their purpose names IN THIS PERMIT'S ORGANIZATION** (`signers.py`, checked before `sign()` is called): strict equality on `users.organization_id`, refusing `sys_admin` too — this is not a permission question but a question about whose signature a legal document bears, and a purpose with no entry in that map is refused rather than left fillable, because the required set is an admin-editable setting and a typo must fail closed. **`service.set_status` is the ONE way any module moves a permit** (`to_status`, `actor`, `reason`, `reason_item_id`, `doc_file_id`, `correlation_id`): it locks the row, validates the edge against `PERMIT_TRANSITIONS`, writes the append-only `permit_status_history` row and audits it. Never `UPDATE permits.status` anywhere; a direct write produces a permit whose timeline cannot explain it, and the missing history row cannot be added afterwards. The two writers inside the module that do not route through it are `_activate` and `jobs.expire_permits`, both asserted against the same table by a test. **Lock order is permit → application, and there is no other order anywhere in `app/`** — a future caller that moves both must keep it or create the first real cycle. **The application reaches `PERMIT_ISSUED` on ACTIVATION, not on issuance** (`tz/05`: «сформировано **и подписано**»); issuance leaves it `PAID`, so nothing may read "a permit exists" as "a permit was issued". `snapshot` is frozen at issuance and is what the PDF says — never read it as live data — and it carries `calculation_id` so the printed amount can be reconciled with the invoice. **The two seams `gis` (3.6a) and `norms` (3.7) left open are registered in `app/event_subscriptions.py`, never in `main.py` and never by an import from below**: nothing outside this module imports `permits.repo`/`permits.models`, and the registration must stay idempotent (a membership check before the append) because the autouse test fixture restores only `events._SUBSCRIBERS` and would otherwise double every provider's answer. Both providers count `active` and nothing else — a `suspended` permit occupies no area and commits no load. Rendering is blocking C code and runs through `asyncio.to_thread`, and the `permit_counters` row lock is held across it, so issuance serialises nationwide behind one row for the length of a render — inherent to a gapless number printed on the document. `ERR-PERM-001` (409) is this module's state-conflict code; a character the bundled fonts cannot draw is a HARD refusal at issuance (`ERR-VAL-001`, naming it — the cure is a wider font set, never a weaker check). Notification codes are DOTTED (`permit.issued`), the bus event it subscribes to is flat (`payment_confirmed`), and the two are not interchangeable. **Permits (3.11b)**: **a lifecycle decision is signed against the ATTEMPT, never against the permit** — `permits.decisions.decide()` mints a fresh `permit_status_history.id` before calling `sign()`, uses it as `object_id` under a NEW `object_type`, `"permit_decision"`, and hands the same id to `set_status(..., history_id=...)`; signing `("permit", permit.id, ...)` directly, the obvious first shape, would let a permit be suspended exactly once in its whole life against `uq_signatures_valid_purpose`. **`service.set_status` gained one parameter for this, `history_id: uuid.UUID | None = None`** — `None` for every caller before this stage (the row's own `default=uuid7` still mints it), a real value ONLY from `decide()`, which must mint it before `sign()` is called and pass the identical id here, or the signature anchors to a row that does not exist. `suspend`/`resume`/`revoke` are `permits.manage` (`executor_head`), gated exactly like the four issuance signature lines: the actor must additionally hold the role the decision's purpose names IN THIS PERMIT'S organization, resolved through `signers.decision_role`, never a literal at the comparison site. **A duplicate (нусха) is the SAME `pdf_file_id`, never a new file and never a re-render** — `ERR-PERM-002` is therefore STILL raised by nothing after this stage, correctly: the duplicate register (`service.issue_duplicate`) only ever points a new row at the bytes that already exist. Every permit-scoped write this module added — the decision, the duplicate, the forest ticket — checks `_assert_organization_in_zone` BEFORE any status or document check, so an out-of-zone caller learns nothing beyond "not yours" (a Critical in this stage's own review: `issue_duplicate` shipped unscoped first and let one leshoz obtain a legally valid copy of another's permit). **`pending_signatures` still has exactly one exit, `active`, and `tz/12` #16 is still open** — `jobs.watch_stalled_permits` notifies the assigned executor once a permit's whole period has elapsed unsigned and moves NOTHING: no status change, no history row, no new edge in `PERMIT_TRANSITIONS`. Do not add `pending_signatures → revoked` as a convenience fix — `permits.application_id` is `UNIQUE`, so it would leave an application `PAID` against a revoked permit with no second permit ever issuable, which is worse than the wedge it would relieve. A forest ticket (ВМҚ 506, `forest_tickets`) is a numbered register entry with `file_id` permanently null until the Agency supplies the form (`tz/12` #36); at most one `active` ticket per permit (`uq_forest_tickets_active`, `ERR-PERM-003`), revoked in the SAME transaction as its permit (never on suspension, which is temporary), and expired by its OWN standalone nightly sweep (`jobs.expire_forest_tickets`) because its period lives inside the permit's but need not end when the permit's does. `extend` (`POST /permits/{id}/extend`) is gated on the permit's HOLDER, never on `permits.manage`/`.issue`, and widened `applications.service.create_draft` as a function (`kind`, `parent_application_id` as keyword-only parameters) rather than on `ApplicationCreate`, which is the citizen-facing body of `POST /applications` under `extra="forbid"` — widening that model instead would let any applicant file `kind="extension"` against an arbitrary permit.
- **Reference data**: read catalogs through `admin.repo`/`admin.service` (or the `/api/v1/refs/*` routes); never re-query `regions`/`organizations`/`classifier_items` from another module's repo. `GET /refs/*` reads with no rule to apply (regions, districts, organizations, activity/livestock types) call `admin.repo` directly from the router — the one router → repo exception to the layering above, made instead of adding an empty pass-through service method. Runtime policy values (session TTLs, lockout thresholds) come from `app/core/settings_store.py` — `get_int(db, "…")`, never from `Settings`. Nothing in reference data is deleted: `status='archived'`, and classifier values are superseded (archive + insert), never rewritten.

## CI

GitHub Actions (`.github/workflows/ci.yml`, stage 3.4): `lint` (single-Alembic-head check + ruff check + format check + pyright + bandit) and `test` (PostGIS service + MinIO, full pytest incl. the migration downgrade→upgrade round-trip) on every push/PR. Keep both green; the round-trip test runs last and wipes the shared test DB by design (collection order is pinned by a hook in `tests/conftest.py`). Git rules — branch/pull/push discipline for the parallel sessions — live in the root `../CLAUDE.md`. In short (decision #47): branch off `dev`, PR back into `dev`; `main` only ever receives `dev` through a release PR; direct commits on either are blocked by `no-commit-to-branch`.
